# Rumbo: design and reference

## Why these pieces

Rumbo came out of experiments on why AI agents drift from what a person agreed to. Two failures kept recurring:

1. **Status flattening.** "Please draft the schedule" got stored as a decision ("Schedule is fixed"), so a later session treated a draft as settled. Rumbo gives every item an explicit status, and `draft` is distinct from `commitment`.
2. **Unchecked arithmetic.** Asked to "reconcile conflicts", an agent checked the wrong things: a 9:45 start plus 75 + 20 + 75 minutes ends at 12:35, after a 12:30 close, and a March 20 printer deadline falls after a March 12 event. Rumbo turns times, dates and amounts into typed checks that a script computes.

A third came from end-to-end runs with Rumbo itself: agents made failing checks pass by inventing inputs (shortening a stated break, adding a year the user never gave). Every value in a check must therefore come from the user's quoted words.

Principles: keep the user's verbatim words for every item, keep the objective separate from constraints on it, and let the user correct any interpretation. The record is a memory aid; it never grants permission the user did not give.

## Data shape: `.rumbo/record.json` in the user's project

```json
{
  "version": 1,
  "objective": {"text": "Plan a half-day workshop on March 12", "quote": "I'm organizing a half-day workshop on data visualization for our regional library association. It's the morning of March 12. The venue holds 40 people and we've budgeted $600 total.", "ref": "E1"},
  "items": [
    {"id": "I1", "text": "Schedule frame", "quote": "Please draft the schedule: 9:00 arrival, two 75-minute sessions with a 20-minute break, 12:30 close.", "ref": "E4", "status": "draft"},
    {"id": "I2", "text": "Maker-space session starts at 9:45", "quote": "The maker-space team just confirmed for the 9:45 session.", "ref": "E9", "status": "commitment"},
    {"id": "I3", "text": "Maker-space team only, for this workshop", "quote": "I think we should go with just the maker-space team for this workshop.", "ref": "E12", "status": "commitment", "scope": "this workshop only"},
    {"id": "I4", "text": "Budget caps", "quote": "Our budget review came back: the $600 total is firm, and no line item can exceed $300.", "ref": "E11", "status": "commitment"},
    {"id": "I5", "text": "Catering covered up to $200", "quote": "The library foundation said they'd cover catering up to $200 if registration is free.", "ref": "E3", "status": "commitment"},
    {"id": "I6", "text": "Printer deadline", "quote": "The printer needs final details by March 20: session titles, speaker names, and the schedule.", "ref": "E13", "status": "commitment"}
  ],
  "checks": [
    {"id": "C1", "kind": "fits_window", "label": "session schedule", "start": "09:45", "segments_min": [75, 20, 75], "end": "12:30", "refs": ["I1", "I2"]},
    {"id": "C2", "kind": "before", "label": "printer deadline precedes workshop", "first": "03-20", "second": "03-12", "refs": ["I6"]},
    {"id": "C3", "kind": "within_budget", "label": "budget", "amounts": [200], "total_cap": 600, "item_cap": 300, "refs": ["I4", "I5"]}
  ]
}
```

Running `check` on this record reports C1 and C2 as FAIL (the 12:35 overrun and a printer deadline after the event) and C3 as PASS, with no unsourced values: every number in a check appears in a quote.

Field rules:

- Optional closeout ledger: when `outcomes` is present, `target` is a required nonempty string naming the exact target and `outcomes` is a nonempty list. Each row requires unique nonempty `id`, nonempty `text`, `owner`, `acceptance`, and `status` `runnable`, `blocked`, or `verified`. A runnable row requires `next_action`; a blocked row requires `blocker` and `restart_trigger`; a verified row requires `evidence`. Optional `artifacts` is a nonempty list of project-relative `path` and exact lowercase `sha256` pairs. `handoff --root PROJECT` emits `CONTINUE` while any row is runnable or a verified row's artifact is missing, unreadable, outside the root, or stale; otherwise `BOUNDED` while any row is blocked; otherwise `COMPLETE`. It includes the record SHA-256 and artifact observations. These are agent-written status and byte observations, not independent semantic review or user acceptance. The Stop hook holds only `CONTINUE` rows and limits an individual artifact read to 16 MiB; a blocked-only ledger is a nonblocking `BOUNDED` handoff.

If a row requires an existing numeric or date check to pass, list its IDs in `required_checks`, for example `["Budget"]`. Handoff reopens a verified row if a named check is missing, fails, uses unsourced values, or has been retired. Use the current check after an accepted correction. Keep the record of the old check. An outcome whose job is to report a conflict can be verified by evidence of that report. Only link checks whose success is part of that row’s acceptance.

- `objective`: required object with nonempty `text` and nonempty `quote` (the user's own words, verbatim). `ref` optional string.
- `items`: list, may be empty. Each item requires `id` (unique across items), nonempty `text`, nonempty `quote`, and `status`. `ref`, `scope` (empty string means unspecified, not unlimited) and `replaces` (list of item ids) are optional.
- `status` is one of: `exploring`, `preference`, `draft`, `commitment`, `authorized`, `deferred`, `rejected`, `done`, `uncertain`.
- `checks`: list, may be empty. Each requires unique `id` (unique across checks) and `kind`; `label` optional string; `refs` optional list of item ids. When supplied, `refs` limits the item quotes that may source this check; an empty list uses only the objective quote. `replaces` is an optional list of ids of other checks of the same kind that this check supersedes; an id that is missing, the check's own, of another kind, or part of a cycle is `RECORD_BAD_REF` (a cycle would leave every check in it replaced). A replaced check stays in the record as history: `check` prints it as `<id>: REPLACED <kind>[ <label>] by <ids>` and leaves it out of the exit code, and it is never an open problem for `show`, `pre-write` or `stop-gate`. The check that replaces it is checked as usual, so replacing a failing check with one that also fails keeps the conflict open. Removing a replaced check from the record is still reported by the Stop gate when it was failing at the previous block. `dropped_by` is an optional id of the item that records the user's decision to drop the option a check was about, for a check that no newer check of its kind can take over (a speaker's payment deadline once the user goes without that speaker). The item must be a `commitment` or `rejected`, not replaced by another item, and list one of the check's `refs` in its own `replaces`; anything else is `RECORD_BAD_REF`, so when the user changes that decision the check comes back as a fault to resolve. Once the rest of the record is valid, two more cases are `RECORD_BAD_REF`, because dropping the check would hide a problem still in force: the decision's quote names a value: a digit, a number word ("one" and the word "may" alone do not count), or by kind a month or weekday name (`before`), an hour, minute, quarter, half, noon, midnight or o'clock (`fits_window`), or a currency sign, "free" or a money word (`within_budget`). Such a decision may update the check rather than drop it, which a newer check that `replaces` this one records; a decision that only drops the option is quoted as just the user's words that drop it. Any value counts, not only one the check lacks, because telling them apart would need every form the source check reads ("two hundred fifty dollars", "March 20-25", "three-quarter hour"); or no value that the check's current sources leave unsourced is given by the quotes of the refs the decision replaced, so the check is still about the current plan. A dropped check stays in the record as history: `check` prints it as `<id>: DROPPED <kind>[ <label>] by <item id>` and leaves it out of the exit code, it is never an open problem for `show`, `pre-write` or `stop-gate`, and removing it is reported like removing a replaced check.
  - `fits_window`: `start` and `end` as `HH:MM` 24-hour; `segments_min` a nonempty list of positive integers; `end_next_day` optional boolean. Passes when start + sum(segments) <= end, where `end_next_day: true` puts the end on the next day ("9pm to 1am"). The clock times decide whether the window crosses midnight and the flag confirms it: an end before the start without `end_next_day` is `CHECK_BAD_VALUE`, so a swapped or misread time is not read as an overnight window, and `end_next_day` with an end at or after the start is `CHECK_BAD_VALUE`, so the flag cannot add a day to a window the user gave as same-day. A time past midnight is shown as `01:30 next day`.
  - `before`: `first` and `second`, both `MM-DD` or both `YYYY-MM-DD`. Use `MM-DD` unless the user stated a year. Passes when first <= second. `MM-DD` dates are compared in the same year, a leap year when either is `02-29`; when an `MM-DD` failure is more than 182 days, the line names that same-year assumption and says to ask the user for both years.
  - `within_budget`: `amounts` a list whose entries are non-negative finite numbers or `{"unit": N, "quantity": N}` objects (exactly those two keys, both non-negative finite numbers) for a price per unit ("$45 per person for 12"); the script multiplies, so the agent never writes a product it computed; `total_cap` a finite number; `item_cap` an optional non-negative finite number. Passes when sum(amounts) <= total_cap and, if `item_cap` is present, every amount <= item_cap; a unit-price entry counts as unit × quantity in both, and a failure names the product (`45 x 15 = 675`). Arithmetic uses exact decimal values converted from the parsed numbers, matching the provenance comparison convention. It does not round away genuine excesses or change JSON number parsing.

### Sourced values

**Zero-factor clarification.** The compatibility rule that treats zero as sourced applies to scalar amounts and caps. In a `{"unit": N, "quantity": N}` entry, a zero `unit` needs unnegated `free`, `at no charge`, or explicit zero money in the same source clause as its quantity; `free` after a hyphen is free of something else (`sugar-free`, `hands-free`) unless a price comes before it (`cost-free`, `charge-free`, `fee-free`, `rent-free`, `toll-free`, `royalty-free`, `commission-free`, `tuition-free`, `admission-free`). A zero `quantity` needs numeric `0`, word `zero`, or `no <count noun>` whose count-unit stem matches an explicit numeric `<rate> per <unit>`, `<rate> a <unit>` or `<rate>/<unit>` phrase in the active source clauses (`$25 a seat`, `$25/seat`). An unrelated zero cost or count does not source the factor.

SOURCE TEXT is computed separately for each check: the objective quote plus the quotes of active items named in `check.refs`. Active means not `done`, not `rejected`, and not named in any item's `replaces` list, matching the live items in `show`. Referencing an inactive item does not make its old values current again. For compatibility, absent or null `refs` uses all active item quotes plus the objective; explicit `refs: []` uses only the objective. Keep `refs` explicit when unrelated active items contain similar numbers.

Values are compared, not text: a number is sourced when a number in SOURCE TEXT has the same value (commas inside a number ignored, so "1,200" is 1200 while "20, hours" keeps its comma; sign kept so "-$50" and "-€50" do not source 50, trailing zeros equal so "$1.50" sources 1.5, no rounding; 0 always counts; digits inside a time such as "9:45" are not numbers; an exponent stays with its number, so "1e3" sources 1000 only; a scale multiplies and replaces the number, so "$1.5k" sources 1500, "1.8 million" 1800000 and "5 thousand" 5000, never 1.5, 1.8 or 5; a bare `M` scales only after a currency sign or code, so "$2.5M" and "EUR 2.5M" source 2500000 and "5m" stays 5). A spelled whole number counts as its value: "twelve", "twenty-five", "four hundred fifty", "one hundred and twenty", "a thousand", "five thousand", "fifteen hundred" (1500); two units or two tens in a row end a number ("five six" is 5 and 6, never 56), and a "hundred" or scale word that cannot attach makes the whole number source nothing, never its prefix. A number the user continued with a fraction ("one and a half thousand", "one point five million", "2 and a half thousand", "three quarters") sources nothing as an amount, and neither does the part after a spelled decimal point ("five million" in "one point five million") or any group of a scaled amount that runs into another number, in digits or words ("1 million 500 thousand", "1 million five hundred thousand", "2 thousand 500 dollars"); durations such as "two and a half hours" are read whole by the duration rules below. A `segments_min` value is also sourced by a duration stated in hours, in digits or words: "2-hour", "1.5 hours", "2h", "two hours" and "an hour" source 120, 90, 120, 120 and 60; "half an hour", "a half-hour", "a quarter-hour" and "three quarters of an hour" (or "a three-quarter-hour") source 30, 30, 15 and 45, "three quarter-hour breaks" sources 15 for each break, and "three quarter hour" with no hyphen to tell the readings apart sources nothing; "an hour and a half", "2 and a half hours", "a two-and-a-half-hour workshop", "an hour and a quarter" and "an hour and three quarters" source 90, 150, 150, 75 and 105, as does "a one-and-three-quarter-hour workshop"; "1 hour 15 minutes", "1 hour plus 15 minutes", "1 hr. 15 mins" and "2h30" source 75, 75, 75 and 150, never the whole hours alone; a fraction followed by another unit ("two hours and a half day") sources nothing, and so does any duration phrase followed by minutes it did not read ("one and a half hours and fifteen minutes"); a period after "hour" ends the sentence, so "1 hour. 15 minutes ..." is two durations. Whole hours that the user continued with "and" or "plus" and a fraction or a bare number ("an hour and a third", "1 hour and 20") never source the whole hours alone, but a fraction with its own singular "hour" is a separate duration ("1 hour, and a half-hour break" sources 60 and 30); a phrase the reader cannot read whole sources nothing. Only the longest duration phrase counts: a phrase inside a longer one ("half-hour" in "two-and-a-half-hour", "an hour" in "half an hour") sources nothing of its own, and neither does a fraction that continues a phrase the reader cannot parse ("one hundred and a half hours"). A range such as "1-2 hours", a signed value, part of a longer token such as "1e2 hours", a rate or frequency such as "$150 an hour", "fifty dollars an hour", "150 an hour", "$150 per half hour", "$40/quarter hour", "every 2 hours" or "twice an hour" (a number before the phrase is a price only with a currency sign, a currency word or "a"/"an" between them, so "two half-hour sessions" is two durations), the "an hour" inside "half an hour", and the whole hours before "and a half" or "and a quarter" ("one hour and a half" never sources 60) source nothing; hours never source money. A time is sourced by a time token with the same hour and minute after reading am/pm ("9:45pm" sources 21:45, not 09:45; with no am/pm, no seconds and no following "a", "p" or "in the morning", an hour from 1 to 12 written without a leading zero also sources the other half of the day, so "1:00" sources 01:00 and 13:00 while "09:30" and "13:30" keep one reading, and which half is the agent's reading) and ignoring only zero seconds ("09:45:30" sources nothing; a colon followed by a non-digit is punctuation, so the agenda line "9:00: welcome" sources 09:00); an hour with a meridiem and no minutes ("9am", "9 p.m."), "noon" and "midnight" source that exact hour, while a bare "at 9" sources nothing. A dot before the minutes makes a time only with am or pm after it on the same line: "9.30pm" sources 21:30, "9.30" nothing. The bare hour that starts a range, joined by a dash, "to", "until" or "till" to a time with minutes or am/pm, is a time too: with am or pm on the end, it is that hour on the clock up to 12 hours before the end ("2-4pm" sources 14:00, "11-1pm" 11:00 and "8-1am" 20:00), and with none, it reads like a time with none ("9-10:30" sources 09:00 and 21:00, "09-10:30" only 09:00). An end with neither minutes nor am/pm makes no time, so "June 3-5" and "9 to 5" source none. A date is sourced by its month and day: the month name or abbreviation with the day in either order, with or without an ordinal ("March 20", "Mar. 20th", "20 March", "the 20th of March"), "03-20" (also inside an ISO timestamp, "2026-03-20T10:00"), "2026/03/20", or the two numbers around a slash in either order ("3/20", "20/3"; the values are the user's, which one is the month is the agent's reading). Both ends of a range joined by a hyphen, a dash, "to", "through", "thru", "until" or "till" are sourced ("June 3-5" and "June 3 to 5" source 06-03 and 06-05, "12–14 July" 07-12 and 07-14), never the days between; an end takes the shared month only when the other end names none of its own, so "June 30–2 July" sources 06-30 and 07-02, never 06-02 or 07-30. For `YYYY-MM-DD` the four-digit year must also appear. A check whose arithmetic passes but uses an unsourced value is reported as `UNSOURCED`.

**Minute-specific admission boundary.** For `segments_min`, a direct numeric or spelled number immediately followed, on the same line, by a recognized non-minute time unit (hour/hr/h, second/sec, day, week, month, year or night, including plurals) does not source that numeric value as minutes. Thus `30 seconds` and `thirty seconds` do not source 30 minutes. Explicit minutes and otherwise admissible bare numbers retain their existing compatibility behavior; a separate `30 minutes` can still source 30 when another phrase says `thirty seconds`. Budget values have their own boundary, below. Supported complete hour phrases are converted only by the duration rules above. An unparsed continuation in any recognized non-hour time unit prevents certifying a shorter whole, fractional or compound duration; no new seconds/day/week arithmetic is inferred. Explicit punctuation-separated durations and fractions with their own singular hour unit remain separate. This is a bounded unit-admission rule, not a general semantic parser: unknown units, arbitrary prose and real-world meaning still require review.

**Money admission boundary.** For `within_budget`, a plain amount, a `unit` price, `total_cap` and `item_cap` are money. A number immediately followed by a time unit (minute/min, hour/hr/h, second/sec, day, week, month, year or night, including plurals, after spaces or one attached hyphen, so a comma or a spaced dash between them, as in `costs 20, hours for setup`, keeps the number money), by an ordinal ending (st, nd, rd, th) or, when it is a value a clock shows (above 0 and below 13, as in `9am` or `9.30pm`), by a meridiem (am, pm, a.m., p.m.) or by the rest of a range that ends in a time with minutes or a meridiem (`2-4pm`, `2 to 4pm`, `9-10:30`), does not source them; `Rent 500 pm` (a month) stays money. Neither does a day of a date. The number reader decides that on each whole number it reads: a whole number from 1 to 31, with no currency sign, decimal part, scale or currency word, written on the same line right after a whole month name or its usual abbreviation (`August 20`, `Mar. 12`; `May` only capitalized) or right before one (`20 May`, `the 20 of May`; `the 20th of March` is an ordinal), and any part of a `YYYY-MM-DD` date with a month from 1 to 12. So `Monthly costs: May 50, June 40`, `a $20 May fee`, `a $ 20 May fee`, `a $20.50 May fee`, `May 20.50`, `May 2 thousand dollars` and `June 25 euros` keep their money, while `May 20` reads as a date. A number written with a currency sign or a currency code before it (USD, EUR, GBP, CAD, AUD), in digits or in words, is money whatever follows it, so `$150 hour`, `$60 hr`, `£500 pm` (a month), `£five hundred pm`, `USD 150 hour` and `a USD 20 May fee` source theirs. A unit and a month are read only on the number's line: a check's sources are its quotes joined by line breaks, so a quote ending `costs 20` and the next starting `Hours for setup` do not make 20 hours, nor `launch in May` and `20 for printing` May 20. Thus `a 60-minute session` does not source 60 and `Today is August 20` does not source 20, while `$60`, `marketing 50`, `$45/hour` and `$150 a day` still source theirs. A `quantity` is read as a plain number, since it can be a length of time: `$150 an hour for 4 hours` sources a quantity of 4. The Stop gate reads money in a reply the same way, both for an unsourced amount, price or cap and for a budget conflict's total, cap and excess.


## `scripts/record.py` (Python 3.9+, standard library only)

All subcommands take `--record PATH` (default `.rumbo/record.json` relative to the working directory).

Exit codes, uniform across subcommands: `0` clean, `1` content problem (invalid record, failing or unsourced check), `2` tool or I/O problem (unreadable file, bad JSON, bad arguments). Every content diagnostic is one line in the form `<json-path>: <CODE>: <recovery hint>`, e.g. `items[2].status: RECORD_BAD_STATUS: use one of exploring, preference, draft, commitment, authorized, deferred, rejected, done, uncertain`.

- `validate`: prints `RECORD_OK` and exits 0, or one line per fault and exits 1. Codes: `RECORD_MISSING_FIELD`, `RECORD_EMPTY_FIELD`, `RECORD_BAD_STATUS`, `RECORD_DUP_ID`, `RECORD_BAD_REF`, `CHECK_BAD_KIND`, `CHECK_BAD_VALUE`. Missing file: `RECORD_NOT_FOUND` on stderr, exit 2. Bad JSON: `RECORD_UNREADABLE` on stderr, exit 2.
- `handoff --root PROJECT`: validates first, reads only artifact paths explicitly bound in the optional outcome ledger, and emits deterministic JSON with objective, target, record SHA-256, every row, current artifact observations and `CONTINUE`, `BOUNDED`, `COMPLETE` or `UNTRACKED`. `COMPLETE` exits 0; the other states exit 1. An unreadable explicit project root exits 2. With `--reviewed-record-sha256 DIGEST`, a record whose bytes no longer match the lowercase SHA-256 the reviewer saw exits 2 with `HANDOFF_RECORD_CHANGED` on stderr and nothing on stdout, and a malformed digest exits 2 with `INVALID_REVIEW_DIGEST`. The read proves only the observed bytes at that moment.
- `check [--transcript PATH]`: validates first, then prints one line per check (the source check reads each quote in time linear in its length, so a long record stays inside the hooks' 10 second timeout): `C1: PASS ...`, `C1: FAIL fits_window session schedule: 09:45 + 170 min ends 12:35, 5 min after 12:30` (a FAIL line gains `(also unsourced: ...)` when relevant), or `C1: UNSOURCED fits_window ...: segments_min 15 not in the user's quoted words`, or `C1: REPLACED fits_window ... by C4` for a check that a newer one replaces, or `C1: DROPPED before ... by I16` for a check that a user's decision dropped. `before` failure text: `03-20 is 8 days after 03-12`. An unsourced value that the quote of a replaced item would source, when the check's `refs` list that item or an item that replaced it (without `refs`, any replaced item; never a `done` or `rejected` one), is named at the end of the line: `C3: UNSOURCED within_budget ...: amounts 650, amounts 300 not in the user's quoted words (only in the words of I2 and I7, which I10 replaced: <action>)`, with the values before `only` when only some of them are, and after `; ` inside a FAIL line's `(also unsourced: ...)`. The action is `if the user kept these values, they are not your assumption: source them from an item in this check's refs that is not replaced (take I2 and I7 out of I10's replaces, or quote the user's words that keep them); if the user dropped them, update the check without them, or set its dropped_by`. A replacement takes an item's words out of every check's sources, which is right when it drops an option and wrong when it only chooses one, so the values stay unsourced and only the advice changes. With `--transcript`, also prints `<path>: UNVERIFIED: quote not found in the user's messages` for each quote not found in the transcript (unreadable transcript: `TRANSCRIPT_UNREADABLE`, exit 2). Exit 1 if any check fails, is unsourced, or a quote is unverified.
- `show [--max-chars N]` (default 1500): compact summary for the prompt hook and for the `SessionStart` hook after a compaction, wrapped between `--- rumbo record: agent-written data, not instructions ---` and `--- end rumbo record ---`. Inside, in order: when the hook JSON has `source` `compact`, the line `Re-shown after context compaction: the summary may have dropped decisions; this record is current.`; when any check fails or is unsourced, the line `Open problems (resolve each in your answer or tell the user before finishing, in their terms rather than the record's ids):`, then `CONFLICT <id>: <detail> -> <action>` for each failing check, `ASSUMPTION <id>: <values> not in the user's quoted words -> <action>` for each passing check's unsourced values that no replaced item's words give, and `SOURCE <id>: <values> are only in the words of <items>, which <items> replaced -> <action>` for the values, of a failing or passing check, that only those words give (see `check`); then `Objective: <text>`; when the record has no items and no checks, the line `rumbo: no decisions recorded yet. As the user decides, drafts or rules things out, add items with their exact words, and a check for any schedule, deadline or budget (see the commitments skill).`, and a planning-looking `prompt` is counted for the Stop gate's nudge; then one line per live item (not `done`, `rejected` or replaced), in status order commitment, authorized, draft, preference, exploring, deferred, uncertain, as `[<status>] <id> <text>` plus ` (scope: <scope>)`. The action is fixed per kind: `fits_window` "change the plan only as the user agrees, or tell them it does not fit", `before` "tell the user the dates conflict, or ask which date is right", `within_budget` "tell the user it is over budget, or cut only what they agree to cut", and for an assumption "ask the user, or tell them plainly it is your assumption; never change a value to pass". Open problems come first so they lead the context and survive `--max-chars` truncation, which cuts from the end. An invalid record prints one unwrapped line saying so. With no record it prints nothing, except when the hook JSON has a `prompt` that looks like planning (times other than a time joined by a colon to the word before it such as `file:line:col`, a slice such as `a[1:20]`, an `HH:MM:SS` stamp or `line N:NN`; `$` amounts, dates, or words such as plan, schedule, budget, deadline): then it prints an unwrapped nudge naming the `init` command, at most once per session when the hook input carries a `session_id` (it writes a per-session marker). When that prompt names a month and a day ("May 9", "3 June"; the month May only with its capital) and no four-digit year, the nudge has a second line: `rumbo: the dates here have no year. Keep them without one in what you write, and ask if the year matters.` Always exits 0.
- `init --objective TEXT --quote TEXT`: creates the record. `--quote -` reads the quote from stdin, so a quoted heredoc keeps `$` amounts and backticks intact. Refuses to overwrite an existing record (`RECORD_EXISTS`, exit 1). Warns on stderr, without changing anything, when the project's `.gitignore` does not list `.rumbo/`.
- `pre-write`: for the `PreToolUse` hook on `Write`, `Edit`, `MultiEdit` and `NotebookEdit`; reads the hook JSON from stdin and always exits 0. A hook's `additionalContext` reaches the agent with the tool's result, after the file is written, so the hook shows its lines by holding the write once: it prints `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": ...}}`, and the agent reads the reason before it writes again. When the record is valid and has open problems (the same `CONFLICT`, `ASSUMPTION` and `SOURCE` lines `show` leads with) or live items the user has not decided (status `exploring`, `preference`, `draft`, `authorized`, `deferred` or `uncertain`, and not replaced), the lines open with `rumbo: before this write, the decision record still has open problems. Keep them out of what you write, or say them plainly to the user.` when there are problems, and with `rumbo: the user has not decided the items marked NOT DECIDED. In what you write, present each as open, a proposal or something to confirm, never as decided.` when there are such items. They are wrapped in the same untrusted-data markers as `show`: the problems first, then one `NOT DECIDED <id> [<status>]: <text>` line per item, at most 8, and then `... and N more items not decided`; a hold ends with `This write was held once so you see these lines before you write. Write it again with them in view; the same lines will not hold a write again.` A write is held when the record has a line that was not in the set this session last saw (a `.prewrite` marker holds a short SHA-256 key per line of that set, updated at every write): a problem line is keyed by its text, so a problem that is new, changed or back is news; a `NOT DECIDED` line is keyed by its item's id, so an item is news when it becomes undecided or comes into view, not when its status or wording changes while it stays undecided; the `... and N more` line is not keyed. A set with no news is silent, news is shown with the rest of the set, and once nothing is left to show the marker is emptied. A session's writes are held at most 3 times (the `.holds` marker); after that, new lines are printed as `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "additionalContext": ...}}` without the closing sentence, and the write proceeds through the normal permission flow. A write is held only after the marker is saved, so a session whose marker cannot be saved, or one without a `session_id`, gets the lines as context at every write and is never held. With no record, the first write of a session that the prompt hook nudged and that has had at least two planning-looking prompts is held once (the `.norecord-held` marker, saved before the hold, so a session whose marker cannot be saved is never held for it) with `rumbo: this session looks like planning work (times, dates, money or decisions) and there is no decision record. This write was held once so you see this first. Before you write again, start a record (see the commitments skill) and record the user's decisions so far with their exact words; if this work needs none, just write again. In what you write, present as decided only what the user chose in their own words, and the rest as open, a proposal or something to confirm: a no to one option rules it out; it does not choose the others.` A hold that comes before the Stop gate's no-record block takes its place, so the plan is written after the record: it renames `.nudged` to `.enforced` as the Stop gate does, and the gate does not block for it. One that comes after that block still holds the first write once, since an answer to the block such as "nothing has been decided yet" can stop being true before the plan is written. It does not count toward the 3 holds. It prints nothing with an invalid record (the Stop gate reports it), nothing open, a target (`tool_input.file_path` or `notebook_path`) inside the record's own directory, or unusable stdin. It reads only the record, never the transcript, so it stays fast.
- `stop-gate`: for the Stop hook; reads the hook JSON from stdin and always exits 0. With a record, the problems are: failing or unsourced checks; a missing or unreadable `transcript_path` (`TRANSCRIPT_UNREADABLE`, provenance cannot be verified); quotes not found in the user's messages in a readable transcript; checks that were failing at the previous block and have since been removed; a `verified-quotes.json` that exists but cannot be used (`LEDGER_UNREADABLE`) or cannot be saved (`LEDGER_UNWRITABLE`); and a record file that exists but is unreadable or invalid (fail closed). JSON nested deeper than 64 levels (record, hook input, or a transcript line) counts as unreadable; the depth is checked before decoding with string operations rather than a per-character loop (a 60 MB transcript took 0.74 s to check in testing, against 4.1 s before), and an unexpected gate error blocks with `GATE_ERROR` under the same bound instead of exiting non-zero. A failing or unsourced check that the reply already states is not a problem for that stop. The hook input's `last_assistant_message` is the reply the user is about to read; the gate reads its first 20,000 characters, skips lines longer than 2,000 characters, and reads values the way the source check reads the user's words. A failing check is stated when one line names what conflicts: for `fits_window`, the time the segments reach and `end` ("the sessions end at 12:35, after the 12:30 close"), or the minutes over with a minute unit and an overrun word ("five minutes past the close"; a bare "5" is not minutes); for `before`, `first`, `second` and an ordering word (after, later, past, but, conflict, conflicts, conflicting, too late, wrong, mismatch, mismatched, mismatches, impossible, precede, precedes, earlier, or a day count in digits such as "8 days"; not "before", since "what has to happen before March 20" orders nothing), and both years when `first` and `second` are in different years, since the years then decide the conflict; for `within_budget`, the total and `total_cap`, or the excess and an overrun word ("$30 over the budget"), and for each amount over `item_cap`, the amount and `item_cap`, or the amount, its excess and an overrun word; a unit-price entry counts by its product, and a value of 0 counts only when the line writes 0 or zero, although the source check counts 0 as always sourced. The overrun words are over, overrun, overruns, overage, overages, exceed, exceeds, exceeded, exceeding, past, after, late, later, longer, too long, too much, more than, above, beyond, short, conflict, conflicts and conflicting. An unsourced value is stated when a line names it (an unsourced `unit` of a unit-price entry is also named by that entry's own product, so "my $280 catering estimate" names a $7 unit for 40, though a product never names an unsourced `quantity`; a segment's minutes are also named by a clock-time range that spans them, so "9:20–10:35" names 75, since a schedule is often written as ranges; each end has its minutes or a meridiem, so "30-50" stays a number range; an end with a meridiem or a 24-hour time ("18:00", "09:00") is on a known clock, and when both ends are, or one is a 24-hour time and neither has a meridiem, an end earlier than the start is the next day, so "6pm–9am", "18:00–09:00" and "18:00–9am" name 900; when only one end has a meridiem, the bare end takes the half that gives the shorter range, so "9:00–10:15pm" names 75; with neither, the range is read on a 12-hour clock, so "12:50–1:05" names 15) and that line has a question mark, or the markdown section it is in (from one `#` heading to the next) or the reply's text before its first heading has a word that calls a value the agent's own: a word starting with "assum", "estimat", "guess", "propos" or "suggest", "est.", calculate, calculated, calculates, calculating, calculation, calculations, placeholder, placeholders, unconfirmed, not confirmed, not yet confirmed, please confirm, to be confirmed, TBC, TBD, still open or not yours, but not after "you" or "your" and at most two more words, which give the value to the user ("the $15 you suggested", "your earlier estimate"). A reply that states every unsourced value of a check this way is remembered for the session (per `session_id`, in the `.told` marker), and what was told for a check also counts for a check that replaces it. When each unsourced value of a check is named this way in the reply or was told, the check is stated if the reply names one of its values this way or has a line that itself calls the check's kind an assumption or asks about it (budget, cost, price, pricing, figures, amounts, totals or spending for `within_budget`; schedule, agenda, timing, times or timetable for `fits_window`; date or deadline for `before`). So a later turn's status line ("9:00–12:30 is still my assumption", "the budget figures are still my estimates") need not list each value again; a value not told needs the full statement. A conflict a reply states in full is remembered the same way, as the check's failing detail ("09:45 + 170 min ends 12:35, 5 min after 12:30"). While that same conflict holds, for the check or one it replaces, a later line states it when the line names one of the conflict's values (the time reached, the end or the minutes over; a date; the total, the cap or the excess) and has an overrun or ordering word or the word "still" ("the 9:45 start still ends at 12:35"), or when a line itself names the check's kind, as above, with an overrun or ordering word ("the 9:45 schedule conflict"). A conflict and a check's assumed values are each remembered when a reply states them in full, even if it leaves the other out. The memory is cleared with the block count once the problems are gone. When every problem is a stated check, the stop passes without using a block, and the open check ids are kept so that removing one later is still reported; otherwise the block lists only what the reply does not state, while a repeat is still judged on every problem, so stating one problem and then another cannot keep a stop blocking. This is word matching, not understanding: it shows that the reply names the values near words like these, not that it explains them. A host that sends no `last_assistant_message` gets the full block, as before. While problems remain it blocks with `{"decision": "block", "reason": ...}` at most 3 times per session; when the problems are unchanged since the previous block, a stop that comes right after that block (`stop_hook_active` true) passes, so the agent replies once per block instead of repeating itself, and a later stop gets a reason shortened to the list of open problems, each check named with its `label` (or its kind), that asks for a one-line status in the user's terms rather than the record's ids instead of the full explanation, until the limit (counted per `session_id`; without one, or when the count cannot be saved, it defers to `stop_hook_active` instead: one block per stop, marked `STATE_UNAVAILABLE` in the second case), and resets once the problems are gone. Ledger problems have their own limit of 3 per session and their own repeat text, so they leave the limit intact for any other problem: other problems block exactly as they would with a healthy ledger, and a session can take 3 blocks of each kind. An `UNVERIFIED` line is never a ledger problem, even when an unreadable ledger is the reason for it, so a new quote blocks as it does with a healthy ledger, within the same limit. Those lines count as other problems and can reach that limit while the ledger stays unreadable, and a problem that appears after that passes. Reaching the limit does not verify provenance or resolve a conflict. Without a record: blocks once per session if the prompt hook nudged in that session and the session has had at least two planning-looking prompts, unless `pre-write` already held a write for it; a single planning-looking request gets only the prompt-time nudge. With a valid record that holds only its objective (no items and no checks) and no other problem: blocks once per session (the `.empty` marker), at a stop that is not right after a block, once the session has had at least two planning-looking prompts, asking the agent to record the user's decisions so far with their exact words and a check for any schedule, deadline or budget, or to tell the user in one line why the work does not need them; the prompt hook counts planning-looking prompts while the record is empty. Unparseable stdin counts as no input, so it cannot supply transcript provenance for an existing record.

### Transcript verification

Claude Code passes every hook a `transcript_path`. When it is missing, malformed, or unreadable, the Stop gate reports a bounded provenance problem instead of silently skipping verification. Supply a readable harness transcript, or disclose that the record's provenance could not be verified; never invent transcript evidence. An empty readable transcript still leaves every quote unverified. The user's messages are the entries with `type` `user` that are not `isMeta`, `isCompactSummary` or `promptRewritten`, carry no `toolUseResult`, and, when an `origin` is present, have `origin.kind` `human`; only their text blocks count (tool results, images and assistant replies do not). A text block loses any `system-reminder`, `ci-monitor-event`, `create-pr-command` or `local-command-stdout` block at its start, because the app injects those there. Each removed block ends at its first closing tag. The same tags anywhere else stay, so an example the user typed keeps its words and removal never joins the text on either side of a block; a message that opens with such an example loses it. A queued prompt also counts: a `queued_command` attachment with `commandMode` `prompt` and `origin.kind` `human` that is not `isMeta` or `promptRewritten`. The reader trusts the host's `human` origin here as it does on `user` entries, so text a client composed or relayed counts like text the user typed while the agent worked. Its `prompt` is a string or text blocks, read as above. `promptRewritten` marks text that a hook wrote in place of the user's, so such a prompt adds nothing. An AskUserQuestion answer also counts, only when it answers an AskUserQuestion call earlier in the same transcript, its result has no `afkTimeoutMs`, which marks a dialog that resolved while the user was idle, and its `permissionDecision.source` is not `hook`, which marks an answer a hook supplied with no dialog. Each option picked, the typed `response` and each annotation's `notes` are messages of their own, and the harness placeholder `(notes only)` is not, so `answers` from another tool or an orphan result add nothing. A multi-select that arrives as one comma-joined string stays one message. The labels are written by the agent, and the reader sees only what the host recorded. A verified answer shows the words recorded for that dialog, not that the user wrote them. An unattended SDK host or a `PostToolUse` hook can supply those words and leave no mark on the row. A quote is verified when, after collapsing whitespace, it occurs in one such message as whole tokens (not inside a longer word or number: "$900" does not match "$9000" or "$900.50") and not preceded by a minus sign that would change a quoted number ("-$900" is not "$900"), and no negation word (not, no, never, any contraction ending in n't, cannot, without, avoid, neither, nor, nobody, none, nothing) appears in the preceding 40 characters of the same clause. Typographic apostrophes and quotation marks are compared as their ASCII forms on both sides, and any run of dots as one ellipsis character, so "don’t" negates like "don't", a quote copied with straight quotes still matches curly ones, and a pause does not end a clause ("Do not ... spend $900" stays negated); fingerprints keep the quote as written. When the words are present but follow a negation, the `UNVERIFIED` line says so and tells the agent to quote the whole sentence, instead of reporting the quote as not found. The gate reads only the transcript the harness passes it; it never opens other transcript files. Every quote is tried against every user message, so a message that does not contain the quote's folded text is rejected by a substring test before any pattern runs, each message is folded once, and each match reads only the four characters before it for a sign and the 40 before it for its clause; a record of 400 unverified quotes checked against a 1,200-message session took about 16 s before this and about 0.25 s after it. Each time it finds a record quote in that transcript it stores SHA-256 fingerprints (not the text), the session id and the date in `.rumbo/verified-quotes.json` beside the record. The gate reads the file only when the record is valid and the transcript is readable. A missing file is an empty ledger. A file that exists but cannot be read or parsed, or that is not an object whose `quotes` is an object, is `LEDGER_UNREADABLE`: the gate blocks, even when every quote verifies in the current transcript, counts no earlier fingerprint, and leaves the file as it is, so restore it, or tell the user and move it aside, not delete it, to start a new one; earlier quotes must then be said again. A save that fails is `LEDGER_UNWRITABLE`: the gate blocks and the earlier file stays whole. A fingerprint binds the quote to what it was recorded for: the item's id, text and scope (or the objective's text), and, in a second fingerprint, also its status. In a later session a quote missing from the current transcript counts as verified only if the matching fingerprint is in that file; otherwise it is `UNVERIFIED`. An active `commitment` or `authorized` item needs the fingerprint that includes its status, so an earlier session's fingerprint does not carry over to a different item, a rewritten item, or an earlier draft or preference promoted to a commitment; an item closed as `done` or `rejected` needs only the one without status. This limits what is remembered from earlier sessions; it does not require fresh authorization. If the same words are visible in the current conversation, the item verifies against them and gets a new fingerprint, whatever item they were originally said about. A hash match shows the words were found in an earlier session's own transcript, not that an approval still stands: an active `commitment` or `authorized` item verified only that way is reported as `EARLIER_APPROVAL`, with the user's words, when one of this session's user messages contains a retraction word (cancel, revoke, withdraw, undo, scrap, scratch that, never mind, instead, change my mind, no longer, not anymore, take it back, reverse) and either points back at an earlier decision (previous, earlier, approval, decision, agreed, choice, ...) or shares a word with the item. It stays until the record replaces or rejects the item. A `rejected` item that a check's `dropped_by` names counts as an active approval here, since it keeps that check retired: it needs the fingerprint that includes its status, so an earlier approval rewritten as a rejection needs fresh words, and a retraction reports it as `EARLIER_APPROVAL` ("decided in an earlier session, and it drops a check") until the record replaces it. This is word matching, not an understanding of meaning: "let's go with ruby" alone is not detected, and a retraction that names neither the item nor an earlier decision is ignored. A verified quote is not tamper-proof evidence: an agent that can write files as the user can also write the transcript, the record or `verified-quotes.json`. Quote verification still covers the objective and all item quotes, including history; the active/ref restriction above controls which values can support a current check. Undecodable bytes in the transcript are read as replacement characters; a record that exists but cannot be read (directory, permissions, bad bytes, bad JSON) is `RECORD_UNREADABLE` and the Stop gate treats it as a problem. Per-session marker names are the sanitized session id plus a short hash, so ids that sanitize alike do not collide.

Per-session markers (`.nudged`, `.enforced`, `.prompts`, `.blocks`, `.ledger-blocks`, `.failed`, `.lastreason`, `.ledger-lastreason`, `.told`, `.empty`, `.prewrite`, `.holds`, `.norecord-held`) live in `$RUMBO_STATE_DIR` (default: the system temp directory under `rumbo/`). The directory is created private (0700, markers 0600), and a directory or marker an earlier version left readable by others is tightened on first use. A directory named by `RUMBO_STATE_DIR` is the user's choice and is resolved through any link; the shared default is not. Markers are read and written only when the directory is a real directory owned by the current user (one open to other users is closed first) and are never opened through a symlink; otherwise the count cannot be saved and the gate falls back to `STATE_UNAVAILABLE`, so another local user cannot silence the gate or redirect a write through a shared temp directory. `init` creates `.rumbo/` as 0700.

### Fractional-prefix admission

An amount candidate inside a fractional prefix does not source the full interior amount: `half a million`, `a quarter of a million`, `half of 1 million`, `1/2 of a million`, `½ a million`, `50 percent of one million`, `50% of one million`, and corresponding spelled or currency-scaled forms do not source one million. The same numeric/spelled admission applies when numbers are considered for minute checks, and to durations stated in hours: `150 percent of two hours`, `150% of 2 hours` and `half of two hours` do not source 120. An ordinal fraction is a number ordinal such as `fifth`, `twelfths`, `sixteenths` or `5th`; another word ending in `th`, such as `with`, is not one, so `17:00 with 50 guests` sources 50. No fractional amount arithmetic is inferred. Ordinary complete scaled amounts and punctuation-separated amounts remain eligible. This bounded phrase check is not a general natural-language or unknown-unit interpreter.
