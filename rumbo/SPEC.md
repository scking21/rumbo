# Rumbo: design and reference

## Why these pieces

Rumbo came out of experiments on why AI agents drift from what a person agreed to. Two failures kept recurring:

1. **Status flattening.** "Please draft the schedule" got stored as a decision ("Schedule is fixed"), so a later session treated a draft as settled. Rumbo gives every item an explicit status, and `draft` is distinct from `commitment`.
2. **Unchecked arithmetic.** Asked to "reconcile conflicts", an agent checked the wrong things: a 9:45 start plus 75 + 20 + 75 minutes ends at 12:35, after a 12:30 close, and a March 20 printer deadline falls after a March 12 event. Rumbo turns times, dates and amounts into typed checks that a script computes.

A third came from end-to-end runs with Rumbo itself: agents made failing checks pass by inventing inputs (shortening a stated break, adding a year the user never gave). Every value in a check must therefore come from the user's quoted words.

Principles: keep the user's verbatim words for every item, keep the objective separate from constraints on it, and let the user correct any interpretation. The record is a memory aid; it never grants permission the user did not give.

## Data shape: `.rumbo/record.json` in the user's project

```json
{
  "version": 1,
  "objective": {"text": "Plan a half-day workshop on March 12", "quote": "I'm organizing a half-day workshop on data visualization for our regional library association. It's the morning of March 12. The venue holds 40 people and we've budgeted $600 total.", "ref": "E1"},
  "items": [
    {"id": "I1", "text": "Schedule frame", "quote": "Please draft the schedule: 9:00 arrival, two 75-minute sessions with a 20-minute break, 12:30 close.", "ref": "E4", "status": "draft"},
    {"id": "I2", "text": "Maker-space session starts at 9:45", "quote": "The maker-space team just confirmed for the 9:45 session.", "ref": "E9", "status": "commitment"},
    {"id": "I3", "text": "Maker-space team only, for this workshop", "quote": "I think we should go with just the maker-space team for this workshop.", "ref": "E12", "status": "commitment", "scope": "this workshop only"},
    {"id": "I4", "text": "Budget caps", "quote": "Our budget review came back: the $600 total is firm, and no line item can exceed $300.", "ref": "E11", "status": "commitment"},
    {"id": "I5", "text": "Catering covered up to $200", "quote": "The library foundation said they'd cover catering up to $200 if registration is free.", "ref": "E3", "status": "commitment"},
    {"id": "I6", "text": "Printer deadline", "quote": "The printer needs final details by March 20: session titles, speaker names, and the schedule.", "ref": "E13", "status": "commitment"}
  ],
  "checks": [
    {"id": "C1", "kind": "fits_window", "label": "session schedule", "start": "09:45", "segments_min": [75, 20, 75], "end": "12:30", "refs": ["I1", "I2"]},
    {"id": "C2", "kind": "before", "label": "printer deadline precedes workshop", "first": "03-20", "second": "03-12", "refs": ["I6"]},
    {"id": "C3", "kind": "within_budget", "label": "budget", "amounts": [200], "total_cap": 600, "item_cap": 300, "refs": ["I4", "I5"]}
  ]
}
```

Running `check` on this record reports C1 and C2 as FAIL (the 12:35 overrun and a printer deadline after the event) and C3 as PASS, with no unsourced values: every number in a check appears in a quote.

Field rules:

- `objective`: required object with nonempty `text` and nonempty `quote` (the user's own words, verbatim). `ref` optional string.
- `items`: list, may be empty. Each item requires `id` (unique across items), nonempty `text`, nonempty `quote`, and `status`. `ref`, `scope` (empty string means unspecified, not unlimited) and `replaces` (list of item ids) are optional.
- `status` is one of: `exploring`, `preference`, `draft`, `commitment`, `authorized`, `deferred`, `rejected`, `done`, `uncertain`.
- `checks`: list, may be empty. Each requires unique `id` (unique across checks) and `kind`; `label` optional string; `refs` optional list of item ids. When supplied, `refs` limits the item quotes that may source this check; an empty list uses only the objective quote.
  - `fits_window`: `start` and `end` as `HH:MM` 24-hour; `segments_min` a nonempty list of positive integers; `end_next_day` optional boolean. Passes when start + sum(segments) <= end, where `end_next_day: true` puts the end on the next day ("9pm to 1am"). The clock times decide whether the window crosses midnight and the flag confirms it: an end before the start without `end_next_day` is `CHECK_BAD_VALUE`, so a swapped or misread time is not read as an overnight window, and `end_next_day` with an end at or after the start is `CHECK_BAD_VALUE`, so the flag cannot add a day to a window the user gave as same-day. A time past midnight is shown as `01:30 next day`.
  - `before`: `first` and `second`, both `MM-DD` or both `YYYY-MM-DD`. Use `MM-DD` unless the user stated a year. Passes when first <= second. `MM-DD` dates are compared in the same year, a leap year when either is `02-29`; when an `MM-DD` failure is more than 182 days, the line names that same-year assumption and says to ask the user for both years.
  - `within_budget`: `amounts` a list whose entries are non-negative finite numbers or `{"unit": N, "quantity": N}` objects (exactly those two keys, both non-negative finite numbers) for a price per unit ("$45 per person for 12"); the script multiplies, so the agent never writes a product it computed; `total_cap` a finite number; `item_cap` an optional non-negative finite number. Passes when sum(amounts) <= total_cap and, if `item_cap` is present, every amount <= item_cap; a unit-price entry counts as unit × quantity in both, and a failure names the product (`45 x 15 = 675`). Arithmetic uses exact decimal values converted from the parsed numbers, matching the provenance comparison convention. It does not round away genuine excesses or change JSON number parsing.

### Sourced values

SOURCE TEXT is computed separately for each check: the objective quote plus the quotes of active items named in `check.refs`. Active means not `done`, not `rejected`, and not named in any item's `replaces` list, matching the live items in `show`. Referencing an inactive item does not make its old values current again. For compatibility, absent or null `refs` uses all active item quotes plus the objective; explicit `refs: []` uses only the objective. Keep `refs` explicit when unrelated active items contain similar numbers.

Values are compared, not text: a number is sourced when a number in SOURCE TEXT has the same value (commas ignored, sign kept so "-$50" and "-€50" do not source 50, trailing zeros equal so "$1.50" sources 1.5, no rounding; 0 always counts; digits inside a time such as "9:45" are not numbers; an exponent stays with its number, so "1e3" sources 1000 only; a scale multiplies and replaces the number, so "$1.5k" sources 1500, "1.8 million" 1800000 and "5 thousand" 5000, never 1.5, 1.8 or 5; a bare `M` scales only after a currency sign, so "$2.5M" sources 2500000 and "5m" stays 5). A spelled whole number counts as its value: "twelve", "twenty-five", "four hundred fifty", "one hundred and twenty", "a thousand", "five thousand", "fifteen hundred" (1500); two units or two tens in a row end a number ("five six" is 5 and 6, never 56), and a "hundred" or scale word that cannot attach makes the whole number source nothing, never its prefix. A number the user continued with a fraction ("one and a half thousand", "one point five million", "2 and a half thousand") sources nothing as an amount; durations such as "two and a half hours" are read whole by the duration rules below. A `segments_min` value is also sourced by a duration stated in hours, in digits or words: "2-hour", "1.5 hours", "2h", "two hours" and "an hour" source 120, 90, 120, 120 and 60; "half an hour", "a half-hour", "a quarter-hour" and "three quarters of an hour" (or "a three-quarter-hour") source 30, 30, 15 and 45, "three quarter-hour breaks" sources 15 for each break, and "three quarter hour" with no hyphen to tell the readings apart sources nothing; "an hour and a half", "2 and a half hours", "a two-and-a-half-hour workshop", "an hour and a quarter" and "an hour and three quarters" source 90, 150, 150, 75 and 105, as does "a one-and-three-quarter-hour workshop"; "1 hour 15 minutes", "1 hour plus 15 minutes", "1 hr. 15 mins" and "2h30" source 75, 75, 75 and 150, never the whole hours alone; a fraction followed by another unit ("two hours and a half day") sources nothing; a period after "hour" ends the sentence, so "1 hour. 15 minutes ..." is two durations. Whole hours that the user continued with "and" or "plus" and a fraction or a bare number ("an hour and a third", "1 hour and 20") never source the whole hours alone, but a fraction with its own singular "hour" is a separate duration ("1 hour, and a half-hour break" sources 60 and 30); a phrase the reader cannot read whole sources nothing. Only the longest duration phrase counts: a phrase inside a longer one ("half-hour" in "two-and-a-half-hour", "an hour" in "half an hour") sources nothing of its own, and neither does a fraction that continues a phrase the reader cannot parse ("one hundred and a half hours"). A range such as "1-2 hours", a signed value, part of a longer token such as "1e2 hours", a rate or frequency such as "$150 an hour", "fifty dollars an hour", "150 an hour", "$150 per half hour", "$40/quarter hour", "every 2 hours" or "twice an hour" (a number before the phrase is a price only with a currency sign, a currency word or "a"/"an" between them, so "two half-hour sessions" is two durations), the "an hour" inside "half an hour", and the whole hours before "and a half" or "and a quarter" ("one hour and a half" never sources 60) source nothing; hours never source money. A time is sourced by a time token with the same hour and minute after reading am/pm ("9:45pm" sources 21:45, not 09:45) and ignoring only zero seconds ("09:45:30" sources nothing; a colon followed by a non-digit is punctuation, so the agenda line "9:00: welcome" sources 09:00); an hour with a meridiem and no minutes ("9am", "9 p.m."), "noon" and "midnight" source that exact hour, while a bare "at 9" sources nothing. A date is sourced by its month and day: the month name or abbreviation with the day in either order, with or without an ordinal ("March 20", "Mar. 20th", "20 March", "the 20th of March"), "03-20", or the two numbers around a slash in either order ("3/20", "20/3"; the values are the user's, which one is the month is the agent's reading). Both ends of a range with a hyphen or dash are sourced ("June 3-5" sources 06-03 and 06-05, "12–14 July" 07-12 and 07-14), never the days between. For `YYYY-MM-DD` the four-digit year must also appear. A check whose arithmetic passes but uses an unsourced value is reported as `UNSOURCED`.

## `scripts/record.py` (Python 3.9+, standard library only)

All subcommands take `--record PATH` (default `.rumbo/record.json` relative to the working directory).

Exit codes, uniform across subcommands: `0` clean, `1` content problem (invalid record, failing or unsourced check), `2` tool or I/O problem (unreadable file, bad JSON, bad arguments). Every content diagnostic is one line in the form `<json-path>: <CODE>: <recovery hint>`, e.g. `items[2].status: RECORD_BAD_STATUS: use one of exploring, preference, draft, commitment, authorized, deferred, rejected, done, uncertain`.

- `validate`: prints `RECORD_OK` and exits 0, or one line per fault and exits 1. Codes: `RECORD_MISSING_FIELD`, `RECORD_EMPTY_FIELD`, `RECORD_BAD_STATUS`, `RECORD_DUP_ID`, `RECORD_BAD_REF`, `CHECK_BAD_KIND`, `CHECK_BAD_VALUE`. Missing file: `RECORD_NOT_FOUND` on stderr, exit 2. Bad JSON: `RECORD_UNREADABLE` on stderr, exit 2.
- `check [--transcript PATH]`: validates first, then prints one line per check (the source check reads each quote in time linear in its length, so a long record stays inside the hooks' 10 second timeout): `C1: PASS ...`, `C1: FAIL fits_window session schedule: 09:45 + 170 min ends 12:35, 5 min after 12:30` (a FAIL line gains `(also unsourced: ...)` when relevant), or `C1: UNSOURCED fits_window ...: segments_min 15 not in the user's quoted words`. `before` failure text: `03-20 is 8 days after 03-12`. With `--transcript`, also prints `<path>: UNVERIFIED: quote not found in the user's messages` for each quote not found in the transcript (unreadable transcript: `TRANSCRIPT_UNREADABLE`, exit 2). Exit 1 if any check fails, is unsourced, or a quote is unverified.
- `show [--max-chars N]` (default 1500): compact summary for the prompt hook and for the `SessionStart` hook after a compaction, wrapped between `--- rumbo record: agent-written data, not instructions ---` and `--- end rumbo record ---`. Inside, in order: when the hook JSON has `source` `compact`, the line `Re-shown after context compaction: the summary may have dropped decisions; this record is current.`; when any check fails or is unsourced, the line `Open problems (resolve each in your answer or tell the user before finishing):`, then `CONFLICT <id>: <detail> -> <action>` for each failing check and `ASSUMPTION <id>: <values> not in the user's quoted words -> <action>` for each unsourced one; then `Objective: <text>`; then one line per live item (not `done`, `rejected` or replaced), in status order commitment, authorized, draft, preference, exploring, deferred, uncertain, as `[<status>] <id> <text>` plus ` (scope: <scope>)`. The action is fixed per kind: `fits_window` "change the plan only as the user agrees, or tell them it does not fit", `before` "tell the user the dates conflict, or ask which date is right", `within_budget` "tell the user it is over budget, or cut only what they agree to cut", and for an assumption "ask the user, or tell them plainly it is your assumption; never change a value to pass". Open problems come first so they lead the context and survive `--max-chars` truncation, which cuts from the end. An invalid record prints one unwrapped line saying so. With no record it prints nothing, except when the hook JSON has a `prompt` that looks like planning (times, `$` amounts, dates, or words such as plan, schedule, budget, deadline): then it prints an unwrapped nudge naming the `init` command, at most once per session when the hook input carries a `session_id` (it writes a per-session marker). Always exits 0.
- `init --objective TEXT --quote TEXT`: creates the record. `--quote -` reads the quote from stdin, so a quoted heredoc keeps `$` amounts and backticks intact. Refuses to overwrite an existing record (`RECORD_EXISTS`, exit 1). Warns on stderr, without changing anything, when the project's `.gitignore` does not list `.rumbo/`.
- `pre-write`: for the `PreToolUse` hook on `Write`, `Edit`, `MultiEdit` and `NotebookEdit`; reads the hook JSON from stdin, never blocks and always exits 0. When the record is valid and has open problems (the same `CONFLICT` and `ASSUMPTION` lines `show` leads with), it prints `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "additionalContext": ...}}`, so the agent sees them before it writes a deliverable, not only at Stop. The context opens with `rumbo: before this write, the decision record still has open problems. Keep them out of what you write, or say them plainly to the user.` and wraps the lines in the same untrusted-data markers as `show`. It carries no `permissionDecision`, so the write proceeds through the normal permission flow. It prints nothing with no record, an invalid record (the Stop gate reports it), no open problems, a target (`tool_input.file_path` or `notebook_path`) inside the record's own directory, or unusable stdin. A given set of open problems is shown once per session (a `.prewrite` marker holds its SHA-256); a changed set is shown again, and once the problems clear the marker is emptied so problems that come back are shown again. Without a `session_id`, or when the marker cannot be read, it shows them every time. It reads only the record, never the transcript, so it stays fast.
- `stop-gate`: for the Stop hook; reads the hook JSON from stdin and always exits 0. With a record, the problems are: failing or unsourced checks; a missing or unreadable `transcript_path` (`TRANSCRIPT_UNREADABLE`, provenance cannot be verified); quotes not found in the user's messages in a readable transcript; checks that were failing at the previous block and have since been removed; a `verified-quotes.json` that exists but cannot be used (`LEDGER_UNREADABLE`) or cannot be saved (`LEDGER_UNWRITABLE`); and a record file that exists but is unreadable or invalid (fail closed). JSON nested deeper than 64 levels (record, hook input, or a transcript line) counts as unreadable, and an unexpected gate error blocks with `GATE_ERROR` under the same bound instead of exiting non-zero. While problems remain it blocks with `{"decision": "block", "reason": ...}` at most 3 times per session; when the problems are unchanged since the previous block, the reason is shortened to the list of open problems and asks for a one-line status instead of the full explanation, so nothing passes without a reply until the limit (counted per `session_id`; without one, or when the count cannot be saved, it defers to `stop_hook_active` instead: one block per stop, marked `STATE_UNAVAILABLE` in the second case), and resets once the problems are gone. Ledger problems have their own limit of 3 per session and their own repeat text, so they leave the limit intact for any other problem: other problems block exactly as they would with a healthy ledger, and a session can take 3 blocks of each kind. An `UNVERIFIED` line is never a ledger problem, even when an unreadable ledger is the reason for it, so a new quote blocks as it does with a healthy ledger, within the same limit. Those lines count as other problems and can reach that limit while the ledger stays unreadable, and a problem that appears after that passes. Reaching the limit does not verify provenance or resolve a conflict. Without a record: blocks once per session if the prompt hook nudged in that session and the session has had at least two planning-looking prompts; a single planning-looking request gets only the prompt-time nudge. Unparseable stdin counts as no input, so it cannot supply transcript provenance for an existing record.

### Transcript verification

Claude Code passes every hook a `transcript_path`. When it is missing, malformed, or unreadable, the Stop gate reports a bounded provenance problem instead of silently skipping verification. Supply a readable harness transcript, or disclose that the record's provenance could not be verified; never invent transcript evidence. An empty readable transcript still leaves every quote unverified. The user's messages are the entries with `type` `user` that are not `isMeta`, `isCompactSummary` or `promptRewritten`, carry no `toolUseResult`, and, when an `origin` is present, have `origin.kind` `human`; only their text blocks count (tool results, images and assistant replies do not). A text block loses any `system-reminder`, `ci-monitor-event`, `create-pr-command` or `local-command-stdout` block at its start, because the app injects those there. Each removed block ends at its first closing tag. The same tags anywhere else stay, so an example the user typed keeps its words and removal never joins the text on either side of a block; a message that opens with such an example loses it. A queued prompt also counts: a `queued_command` attachment with `commandMode` `prompt` and `origin.kind` `human` that is not `isMeta` or `promptRewritten`. The reader trusts the host's `human` origin here as it does on `user` entries, so text a client composed or relayed counts like text the user typed while the agent worked. Its `prompt` is a string or text blocks, read as above. `promptRewritten` marks text that a hook wrote in place of the user's, so such a prompt adds nothing. An AskUserQuestion answer also counts, only when it answers an AskUserQuestion call earlier in the same transcript, its result has no `afkTimeoutMs`, which marks a dialog that resolved while the user was idle, and its `permissionDecision.source` is not `hook`, which marks an answer a hook supplied with no dialog. Each option picked, the typed `response` and each annotation's `notes` are messages of their own, and the harness placeholder `(notes only)` is not, so `answers` from another tool or an orphan result add nothing. A multi-select that arrives as one comma-joined string stays one message. The labels are written by the agent, and the reader sees only what the host recorded. A verified answer shows the words recorded for that dialog, not that the user wrote them. An unattended SDK host or a `PostToolUse` hook can supply those words and leave no mark on the row. A quote is verified when, after collapsing whitespace, it occurs in one such message as whole tokens (not inside a longer word or number: "$900" does not match "$9000" or "$900.50") and not preceded by a minus sign that would change a quoted number ("-$900" is not "$900"), and no negation word (not, no, never, any contraction ending in n't, cannot, without, avoid, neither, nor, nobody, none, nothing) appears in the preceding 40 characters of the same clause. Typographic apostrophes and quotation marks are compared as their ASCII forms on both sides, and any run of dots as one ellipsis character, so "don’t" negates like "don't", a quote copied with straight quotes still matches curly ones, and a pause does not end a clause ("Do not ... spend $900" stays negated); fingerprints keep the quote as written. When the words are present but follow a negation, the `UNVERIFIED` line says so and tells the agent to quote the whole sentence, instead of reporting the quote as not found. The gate reads only the transcript the harness passes it; it never opens other transcript files. Each time it finds a record quote in that transcript it stores SHA-256 fingerprints (not the text), the session id and the date in `.rumbo/verified-quotes.json` beside the record. The gate reads the file only when the record is valid and the transcript is readable. A missing file is an empty ledger. A file that exists but cannot be read or parsed, or that is not an object whose `quotes` is an object, is `LEDGER_UNREADABLE`: the gate blocks, even when every quote verifies in the current transcript, counts no earlier fingerprint, and leaves the file as it is, so restore it, or tell the user and move it aside, not delete it, to start a new one; earlier quotes must then be said again. A save that fails is `LEDGER_UNWRITABLE`: the gate blocks and the earlier file stays whole. A fingerprint binds the quote to what it was recorded for: the item's id, text and scope (or the objective's text), and, in a second fingerprint, also its status. In a later session a quote missing from the current transcript counts as verified only if the matching fingerprint is in that file; otherwise it is `UNVERIFIED`. An active `commitment` or `authorized` item needs the fingerprint that includes its status, so an earlier session's fingerprint does not carry over to a different item, a rewritten item, or an earlier draft or preference promoted to a commitment; an item closed as `done` or `rejected` needs only the one without status. This limits what is remembered from earlier sessions; it does not require fresh authorization. If the same words are visible in the current conversation, the item verifies against them and gets a new fingerprint, whatever item they were originally said about. A hash match shows the words were found in an earlier session's own transcript, not that an approval still stands: an active `commitment` or `authorized` item verified only that way is reported as `EARLIER_APPROVAL`, with the user's words, when one of this session's user messages contains a retraction word (cancel, revoke, withdraw, undo, scrap, scratch that, never mind, instead, change my mind, no longer, not anymore, take it back, reverse) and either points back at an earlier decision (previous, earlier, before, approval, decision, agreed, choice, ...) or shares a word with the item. It stays until the record replaces or rejects the item. This is word matching, not an understanding of meaning: "let's go with ruby" alone is not detected, and a retraction that names neither the item nor an earlier decision is ignored. A verified quote is not tamper-proof evidence: an agent that can write files as the user can also write the transcript, the record or `verified-quotes.json`. Quote verification still covers the objective and all item quotes, including history; the active/ref restriction above controls which values can support a current check. Undecodable bytes in the transcript are read as replacement characters; a record that exists but cannot be read (directory, permissions, bad bytes, bad JSON) is `RECORD_UNREADABLE` and the Stop gate treats it as a problem. Per-session marker names are the sanitized session id plus a short hash, so ids that sanitize alike do not collide.

Per-session markers (`.nudged`, `.enforced`, `.prompts`, `.blocks`, `.ledger-blocks`, `.failed`, `.lastreason`, `.ledger-lastreason`, `.prewrite`) live in `$RUMBO_STATE_DIR` (default: the system temp directory under `rumbo/`). The directory is created private (0700, markers 0600), and a directory or marker an earlier version left readable by others is tightened on first use. A directory named by `RUMBO_STATE_DIR` is the user's choice and is resolved through any link; the shared default is not. Markers are read and written only when the directory is a real directory owned by the current user (one open to other users is closed first) and are never opened through a symlink; otherwise the count cannot be saved and the gate falls back to `STATE_UNAVAILABLE`, so another local user cannot silence the gate or redirect a write through a shared temp directory. `init` creates `.rumbo/` as 0700.

## Tests

`python3 -m unittest discover -s tests -v` from the plugin root. Tests run the script as a subprocess in temporary directories and cover every validation code, check kind, the source check, the nudge and its once-per-session enforcement, the stop gate, and the workshop fixture in `tests/fixtures/workshop.json`.

## Packaging

- `.claude-plugin/plugin.json`: name `rumbo`, version `0.3.9`, MIT; `.claude-plugin/icon.svg` is the listing icon.
- `hooks/hooks.json`: `UserPromptSubmit` runs `"${CLAUDE_PLUGIN_ROOT}"/scripts/show.sh`; `SessionStart` with matcher `compact` runs the same `show.sh`, so the record is back in context right after a compaction, even in the middle of a long autonomous turn when no new prompt arrives; `PreToolUse` with matcher `Write|Edit|MultiEdit|NotebookEdit` runs `"${CLAUDE_PLUGIN_ROOT}"/scripts/pre-write.sh`; `Stop` runs `"${CLAUDE_PLUGIN_ROOT}"/scripts/stop-gate.sh`. Each is a two-line shell script that runs `record.py` against `${CLAUDE_PROJECT_DIR}/.rumbo/record.json`; the hook command itself names only a literal path inside the plugin, as the directory validator requires.
- `skills/commitments/SKILL.md`: when and how the agent maintains the record.
- The repository root's `.claude-plugin/marketplace.json` lists `rumbo` with source `./rumbo`.
