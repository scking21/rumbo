## New changes

- Python core 0.3.3 packages a board that ignores superseded asynchronous refresh results and errors.
- OpenAI local adapter 0.3.4 bundles that core and board. The Sites source board also keeps the latest selected project when older responses arrive later.
- Claude adapter 0.3.5 rejects nonfinite budget inputs, treats malformed non-decimal clock digits as validation faults, and evaluates finite budget values using exact decimal arithmetic. Equality at the cap passes; a genuine excess, however small, still fails.

Budget conversion follows the existing provenance convention, Decimal(str(parsed_value)). JSON number parsing is unchanged; this does not add arbitrary-precision parsing of original floating-point literals. The expanded natural-language date/time/amount recognition from PR10 remains intact.

The three new versions distinguish this follow-on from the already merged core0.3.2/OpenAI0.3.3/Claude0.3.4 distribution identities. Dependency pins, storage formats, authority boundaries and registry bindings are unchanged. No deployment, marketplace submission or installed-host update is established by source versions.

## October 15 receipt and review follow-up

The candidate adds optional `response_mode: "receipt"` to supported mutation tools in the Python and Sites catalogs. Omission or `"snapshot"` keeps the existing full snapshot response. The `tools/list` schemas are larger even for clients that do not opt in; component versions are unchanged within this still-unpublished candidate. The local, public-submission and Sites-review-draft package notes all disclose this optional catalog change. See [mutation receipt v1](MUTATION-RECEIPTS-v1.md) for the exact supported operations and recovery arguments.

A `rumbo.mutation_receipt.v1` response is an incomplete operation-time observation, not complete project context, a freshness guarantee, an idempotency key or human acceptance. Read full state through `rumbo_state` when context is missing or stale, or after an interrupted mutation response before considering a retry. Boards continue to request full state. No token, latency or cost improvement is established.

The review follow-up also prevents a delayed initial host tool result or error from replacing a newer explicit board refresh or discarding its response. Later host updates still supersede older in-flight reads. This applies to both local and Sites board sources; synthetic DOM/protocol regression tests are distinct from native-browser or installed-host verification.

The hosted review follow-up also makes an early Refresh recover its own project context: without a known project key, it uses the existing read-only `open_project_board` discovery call, which returns the authorized project snapshot or project selector. Once a project key is available, Refresh continues to use keyed `rumbo_state`. A transient early failure can retry discovery even if the delayed initial result was already suppressed. Regression coverage exercises the actual hosted dispatcher and SQLite-backed storage, including zero, one and multiple authorized projects, and verifies no database writes during discovery, selection or refresh.
