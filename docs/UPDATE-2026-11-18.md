# November 18 Stop gate and per-task staleness

This source candidate builds on main `2398b05fc2f16f98a628d83a276620f0e5fb1601`. It changes when the Claude adapter's Stop gate blocks a repeat, and it adds an opt-in staleness rule to the Python engine. It does not change protocol versions, the record format or tools.

## Prepared distribution identities

- The Claude adapter **0.3.9** carries the Stop gate change in `rumbo/scripts/record.py`, with `rumbo/SPEC.md` and the commitments skill updated to match.
- The Python engine/package stays **0.3.5**. Its source gains the opt-in `revision_scope` described below. A contract that does not set it behaves as before.
- The OpenAI portable and Codex local adapters **0.3.6** and the isolated Sites candidate **0.1.3** are unchanged. The hosted Sites runtime does not support `revision_scope`.

## What changed

- **Stop gate.** When the problems are unchanged since the previous block, a stop that comes right after that block now passes. Before, it blocked again with a one-line status request, up to the session's three blocks, so an agent could spend all three repeating itself in one turn. A later stop with the same open problems still gets the one-line status block, and the limit of three blocks per session is unchanged. The gate does not check what the agent said in reply.
- **Per-task staleness.** A contract with `"revision_scope": "task"` stamps each artifact, evidence item and decision with a fingerprint of the task's id, title, dependencies and acceptance criteria plus the shared goal and constraints. A revision then makes a task stale only when its fingerprint changes. The owner portal keeps the field when it prefills a revision, and the board marks records as historical against the task's current fingerprint. `docs/PROTOTYPE-CORE-IDEA.md` has the live-session results behind both changes.

## Verification, packaging and rollback

Run the Claude-adapter suite from `rumbo/`, the engine suite and the release identity checks from the repository root.

```sh
(cd rumbo && python3 -m unittest discover -s tests)
python3 -m unittest discover -s tests
python3 -m unittest tests.test_release_identity
```

The Claude directory reads the plugin from `rumbo/` on main. No OpenAI submission, approval or Sites deployment is claimed. To roll back, return to `2398b05fc2f16f98a628d83a276620f0e5fb1601`. There is no data migration; a ledger that used `revision_scope` reads under the old rule, where every revision stales every task.

Two consequences of per-task staleness to know before relying on it:

- **Staleness follows content, not history.** If a revision rewords a task and a later revision restores the exact earlier wording, that task's earlier artifact, evidence and acceptance apply again without new work. This is intended: what was accepted matches what is agreed again.
- **Rolling forward after a rollback can flip statuses.** Work registered or accepted while the ledger was read by the old code carries no task fingerprint. When the new code reads that ledger again, it treats that work as stale, while work stamped before the rollback can read as accepted again. After a rollback and return, check the board and have the owner re-accept anything the old code accepted.
