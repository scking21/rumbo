# Codex-local commitments

This is an explicit workflow, not automatic enforcement. Invoke it when the user asks to track commitments, check a plan, or recover agreed decisions. Claude lifecycle hooks are not installed here. Remote-only/hosted MCP cannot execute this skill's local helper; use its supported coordination tools instead.

Resolve `../../scripts/commitments.py` relative to this installed SKILL.md directory. Use an absolute resolved helper path and the authorized project's explicit record path. Do not guess a plugin environment variable, use the current directory as proof of project ownership, or read private session directories. Python 3.9+ and the bundled stdlib-only runtime are required; missing dependencies are not authority to install them.

## Recover and preserve

Read the authorized project's `.rumbo/record.json` before changing it. If it exists, preserve all decisions, quote references, statuses and replacement history. Use only accessible conversation evidence supplied by the user or an authorized export. Record requested/planned work separately from verified completion. No transcript verification is provided by this adapter: matching a recorded quote to a value does not prove that quote came from the user.

When a new record is authorized, run `python3 /absolute/plugin/scripts/commitments.py init --record /absolute/project/.rumbo/record.json --objective 'Objective' --quote -` and supply the exact quote over stdin. In a shell, use a quoted heredoc delimiter such as `<<'QUOTE'` so dollar signs and backticks remain literal. Never overwrite an existing record to initialize again.

After initialization inspect the record's actual schema before editing. Preserve the objective's `quote`, each item's verbatim `quote`, stable `id`, optional source `ref`, and `replaces` list. Each check's `refs` lists its supporting item IDs; `refs: []` sources only the objective. Missing or null `refs` retains the legacy all-active-items behavior. Done, rejected and replaced items cannot source checks. A check may list older checks of the same kind in its own `replaces`; one about an option the user dropped may name, in `dropped_by`, the item recording that decision, which must replace one of the check's refs and whose quote names no value of the check's kind. Both stay as history, and `check` prints them as REPLACED or DROPPED. Preserve explicit statuses: exploring, preference, draft, commitment, authorized, deferred, rejected, done, uncertain. Retain superseded items with their replacement link. Do not promote a preference into authorization or a plan into completion.

For a multi-deliverable or delegated request, keep one optional top-level `outcomes` row per requested result and a nonempty top-level `target` naming the exact project or artifact target. Each row needs `id`, `text`, `owner`, `acceptance`, and `status`: `runnable`, `blocked`, or `verified`. A runnable row needs its exact `next_action`. A blocked row needs both `blocker` and `restart_trigger`; a blocker on one row does not close or pause unrelated runnable rows. A verified row needs concise exact `evidence`. When evidence is a local project file, add `artifacts: [{"path":"project/relative/file","sha256":"..."}]` so handoff can read the current bytes. Do not mark a row verified merely because a worker returned, a command ran, a checkpoint exists, or a different row is blocked.

If a row requires an existing numeric or date check to pass, list its IDs in `required_checks`, for example `["Budget"]`. Handoff reopens a verified row if a named check is missing, fails, uses unsourced values, or has been retired. Use the current check after an accepted correction. Keep the record of the old check. An outcome whose job is to report a conflict can be verified by evidence of that report. Only link checks whose success is part of that row’s acceptance.

## Check bounded units

Run `validate --record PATH` after an authorized record edit. Run `check --record PATH` before using a plan, schedule or budget in an answer, and `show --record PATH --max-chars 3000` to recover context after a break. Use the same absolute helper prefix for each command.

Supported deterministic checks include `fits_window` (explicit `end_next_day: true` for an overnight window), `before` with real dates, and `within_budget` with exact decimal amounts or `unit * quantity`. Populate a check only when its values, units and quote references are supported. Inspect the validator's diagnostics rather than inventing schema fields. Tests of numeric consistency are not independent proof of the underlying facts or a complete natural-language interpretation.

On a conflict or unknown result, preserve the failing record, explain the exact uncertainty, and fix only from evidence or ask the smallest necessary question. Never delete a commitment, change its status, weaken a check or invent a quote merely to get a pass. Review the full record if the compact view is truncated. Before a final answer, confirm the actual check output and unresolved issues; command completion alone is not task completion.

Before a handoff or closeout, run `handoff --record PATH --root /absolute/authorized/project`. For a project’s standard `.rumbo/record.json`, the root must identify the directory containing `.rumbo`. If the helper reports `HANDOFF_PROJECT_MISMATCH`, recover both paths from the intended project before retrying. It emits the objective, target, exact record SHA-256, every outcome row, current artifact observations, and one overall state. When asked to sign off on an exact previously reviewed record, pass its retained digest as `--reviewed-record-sha256 HEX`. On `HANDOFF_RECORD_CHANGED`, inspect the current changes before signing off. Continue unrelated authorized work. For an ordinary current-state handoff, omit the option so legitimate updates proceed. `CONTINUE` means at least one row remains runnable, including a row whose recorded evidence hash is stale. Keep working or hand it to the named owner. `BOUNDED` means no row is runnable but at least one has a specific blocker and restart trigger; report that boundary without calling the whole request complete. `COMPLETE` means every recorded row is verified against any bound artifact bytes. It proves neither that the outcome inventory is exhaustive nor that evidence is semantically correct, independently reviewed, accepted by the user, or still unchanged after the read.

This helper exposes only init, validate, check, show and handoff. It has no Claude Stop/PreToolUse hook, no background listener, no transcript path option, no model invocation and no additional MCP authority. Local Codex must invoke handoff explicitly. Use the separate coordination/review skills for project aliases, task claims, artifact evidence and reviewer roles.
